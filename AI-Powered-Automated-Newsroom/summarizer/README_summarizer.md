## Overview

This module takes clusters of Arabic and French news articles produced by the embedding pipeline, translates them to English, and generates a concise 2–3 sentence English digest for each cluster. It follows the pipeline architecture defined in the project specification:

```
Cluster Retrieval → Article Concatenation → Language Detection & Transformation
      → Model Selection → Summary Generation → DB Write-back
```

## Architecture

### Phase 1 — Cluster Retrieval (`pipeline.py`)

Fetches all clusters from Supabase that do not yet have an entry in the `summaries` table. For each cluster, fetches its articles from the `articles` table.

### Phase 2 — Article Concatenation (`preprocessor.py`)

Articles are not simply joined end-to-end. The concatenation strategy is **centroid-ranked + extractive-compressed**:

1. Each article is scored by cosine similarity to the cluster centroid embedding (reusing the multilingual MiniLM model already loaded by the embedding pipeline).
2. Articles are sorted by relevance — most central articles appear first.
3. For each article, the 2 most informative sentences are extracted (again by centroid similarity).
4. Concatenation stops when the token budget (~900 tokens) is reached.

**Why not just truncate?** Naive truncation discards articles from the end of the list, which may be the most informative. Centroid-ranked truncation ensures the model always receives the most representative content, not just whatever was scraped first.

### Phase 3 — Language Detection & Transformation (`preprocessor.py`)

Every article is processed individually:

1. **Language detection** via `langdetect` (fast, offline, no API key needed).
2. **Translation to English** via Helsinki-NLP MarianMT models:
   - Arabic → English: `Helsinki-NLP/opus-mt-ar-en`
   - French → English: `Helsinki-NLP/opus-mt-fr-en`

**Why translate to English first?**

| Factor | Multilingual (mT5/mBART) | English-first (MarianMT + BART) |
|---|---|---|
| Summarizer quality | Moderate | High (BART-CNN is SOTA for news) |
| Named entity preservation | Moderate | Better (translation then generation) |
| Language consistency | Inconsistent (mT5 often outputs EN anyway) | Always English |
| Debugging | Hard | Easy — you can read the output |
| Evaluation (ROUGE) | Complex | Straightforward |
| GPU requirement | Recommended | Not required |

MarianMT quality is sufficient for meaning transfer on news text. The translation artifacts only affect the intermediate representation — the final summary is generated by BART, not the translator.

### Phase 4 — Model Selection (`router.py`)

The router applies this decision table:

| Condition | Strategy | Reason |
|---|---|---|
| 1 article in cluster | Extractive only | Nothing to merge; no generation needed |
| 2–4 articles, any tag | Hybrid (BART) | Small cluster; BART handles well |
| ≥5 articles, political tag | LLM (OpenRouter/Groq) | Neutrality requirement |
| ≥5 articles, other tags | Hybrid (BART) | Cost-effective; quality sufficient |
| LLM fails / no API key | Hybrid (BART) fallback | Resilience |

**Is LLMs-only-for-politics a valid decision?**

Yes. Political news has specific requirements that justify the extra cost:
- **Neutrality**: BART inherits the framing of CNN/DailyMail training data. An LLM can be explicitly instructed to be neutral via the system prompt.
- **Entity accuracy**: Names of ministers, parties, and officials must be exact. LLMs handle this better than seq2seq models.
- **Token cost is manageable**: Political clusters are a minority of daily volume (~10–15% by typical news distribution). At ~500 tokens per cluster, this costs ~5,000 tokens/day — well within the free tier of both OpenRouter and Groq.

### Phase 5 — Summary Generation

**Hybrid (`hybrid.py`)**

Two-step process:

```
English concatenated text (~900 tokens)
        ↓
[Extractive compression — top-6 sentences by centroid similarity]
        ↓
Compressed input (~100–150 tokens)
        ↓
[facebook/bart-large-cnn — beam search, 4 beams, no repeat ngrams]
        ↓
2–3 sentence English digest
```

The extractive step is the key improvement over pure abstractive: it selects facts from across the full cluster before BART ever sees the text, so truncation cannot remove important information. This directly reduces hallucination because the model works on curated facts rather than filling gaps from incomplete input.

`sshleifer/distilbart-cnn-12-6` is available as a CPU-friendly alternative (6× faster, slightly lower quality) via the `SUMMARIZER_USE_DISTIL=true` environment variable.

**LLM (`llm.py`)**

Sends a structured prompt to the chosen LLM via the OpenAI-compatible chat completions API:

```
System: neutral news editor, preserve entities, output only summary
User:   [Article 1 — El Khabar] title + content[:400]
        [Article 2 — TSA] title + content[:400]
        ...
        Summary:
```

`temperature=0.3` is used to balance factual accuracy with readability. Articles are capped at 8 to stay within free tier token limits.

### Phase 6 — DB Write-back (`pipeline.py`)

Upserts into the `summaries` table (see schema below). On conflict on `cluster_id`, the existing summary is overwritten — the pipeline is idempotent and safe to re-run.

## Summaries Table Schema

```sql
CREATE TABLE summaries (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    cluster_id      INT4    NOT NULL REFERENCES clusters(cluster_id) ON DELETE CASCADE,
    summary_text    TEXT    NOT NULL,
    summary_lang    VARCHAR(10)  NOT NULL DEFAULT 'en',
    summary_model   VARCHAR(150) NOT NULL,
    strategy        VARCHAR(20)  NOT NULL CHECK (strategy IN ('extractive','hybrid','llm','none')),
    summarized_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    CONSTRAINT summaries_cluster_id_unique UNIQUE (cluster_id)
);
```

**Why a separate table and not columns on `clusters`?**

1. The `clusters` table already has a clear responsibility: clustering metadata. Summaries are a downstream product.
2. A separate table allows multiple summaries per cluster in the future (e.g., A/B testing BART vs LLM output).
3. The `strategy` and `summary_model` columns are only meaningful for summaries, not clusters.
4. Upsert logic on a dedicated table is cleaner than ALTER TABLE + nullable columns.

**Column meanings:**

| Column | Example value | Purpose |
|---|---|---|
| `cluster_id` | `42` | Foreign key to clusters table |
| `summary_text` | `"Algeria launched a 3000 MW solar..."` | The generated digest |
| `summary_lang` | `"en"` | Language of output (always en in current pipeline) |
| `summary_model` | `"hybrid/facebook/bart-large-cnn"` | Full model path for reproducibility |
| `strategy` | `"hybrid"` | High-level strategy used |
| `summarized_at` | `"2026-04-08T14:32:11Z"` | When the summary was generated |

## Libraries Used and Justification

| Library | Version | Role | Why |
|---|---|---|---|
| `langdetect` | ≥1.0.9 | Language detection | Offline, fast, no API key, sufficient accuracy for news text |
| `sentence-transformers` | ≥2.2 | Sentence embeddings for extractive scoring | Same model used in embedding pipeline — no extra memory cost |
| `transformers` | ≥4.35 | MarianMT translation + BART generation | Unified HuggingFace API for all transformer models |
| `sentencepiece` | ≥0.1.99 | Tokenizer dependency for MarianMT | Required by Marian tokenizer |
| `scikit-learn` | ≥1.3 | Cosine similarity computation | Already in project dependencies |
| `openai` | ≥1.0 | OpenAI-compatible client for OpenRouter/Groq | Both providers expose OpenAI-compatible API |
| `supabase` | ≥2.0 | DB read/write | Already used in embedding pipeline |
| `python-dotenv` | ≥1.0 | Environment variable loading | Already used in project |

## Setup

### 1. Install dependencies

```bash
pip install langdetect sentence-transformers transformers sentencepiece scikit-learn openai supabase python-dotenv torch
```

For CPU-only (no CUDA):
```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
```

### 2. Environment variables

Add to your `.env`:

```env
# Supabase (already set from embedding pipeline)
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your-anon-or-service-key

# LLM provider — choose one
LLM_PROVIDER=openrouter         # or "groq"
OPENROUTER_API_KEY=sk-or-...    # from https://openrouter.ai/keys
GROQ_API_KEY=gsk_...            # from https://console.groq.com/keys

# Optional overrides
LLM_MODEL=mistralai/mistral-7b-instruct   # OpenRouter free model
SUMMARIZER_USE_DISTIL=false               # set true for faster CPU inference
```

### 3. Create the summaries table in Supabase

Run `schema_summaries.sql` in the Supabase SQL editor.

### 4. Run

```bash
# From project root
python -m summarizer.pipeline

# Or test with a single cluster
python -c "
from summarizer.router import route_and_summarize
articles = [{'title': 'Test', 'content': 'Test content', 'lang': 'en', 'source': 'test'}]
print(route_and_summarize(articles, cluster_tag='sports'))
"
```

## Free Tier Notes

**OpenRouter free models** (as of 2026):
- `mistralai/mistral-7b-instruct` — good quality, free
- `google/gemma-3-4b-it` — fast, free
- `meta-llama/llama-3.1-8b-instruct:free` — strong, free

- `llama-3.1-8b-instant` — extremely fast (LPU hardware)
- `mixtral-8x7b-32768` — good quality

Both are more than sufficient for 2–3 sentence news digests. The political category filter ensures you only spend LLM tokens where they matter most.
